Topic 1: The Node.js Event Loop

This is the single most asked Node.js topic. You must be able to explain it precisely, not vaguely.

The 6 Phases (in order)

  1. [MUST KNOW] Timers: Executes callbacks scheduled by setTimeout() and setInterval(). Runs callbacks whose threshold has passed.
  2. [MUST KNOW] Pending Callbacks: Executes I/O callbacks deferred to next loop iteration (e.g., some TCP errors).
  3. Idle, Prepare: Internal use only. Ignore for interviews.
  4. [MUST KNOW] Poll: Retrieve new I/O events. Execute I/O-related callbacks. Node waits here if queue is empty (unless timers are due). This is where most of your async work completes.
  5. [MUST KNOW] Check: Executes setImmediate() callbacks.
  6. [MUST KNOW] Close Callbacks: Close events (e.g., socket.on('close', ...)).

Microtask Queue (runs between every phase)

  • [MUST KNOW] process.nextTick(): Runs before any I/O, before the next event loop phase. Highest priority. Can starve the event loop if called recursively.
  • [MUST KNOW] Promise callbacks (.then/.catch): Microtask queue. Runs after process.nextTick() queue is empty. Runs before the next event loop phase.
  • Execution order: process.nextTick → Promise microtasks → Next event loop phase → setImmediate → setTimeout
Q: What is the output of this code? Explain why.
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
process.nextTick(() => console.log('4'));
console.log('5');
Output: 1, 5, 4, 3, 2
Synchronous code runs first: 1, 5. Then microtask queues are drained: process.nextTick runs first (4), then Promise microtasks (3). Then the event loop continues to timers phase: setTimeout callback (2). The key insight: microtasks (nextTick + Promises) always run before the next event loop phase, which is why 4 and 3 appear before 2 even though setTimeout(fn, 0) is registered first.
Q: setImmediate vs setTimeout(fn, 0) — what's the difference?
Answer: setTimeout(fn, 0) runs in the Timers phase of the next event loop iteration — but the actual minimum delay is at least 1ms (and can be up to 4ms in browsers or under load). setImmediate() runs in the Check phase, after the Poll phase. In practice: when called from the main module, the order is non-deterministic because it depends on timing. When called from within an I/O callback, setImmediate() always runs before setTimeout(fn, 0) — because after I/O callbacks (Poll phase) comes Check phase, then the loop restarts for Timers. Use setImmediate() when you want to defer after I/O processing. Use process.nextTick() when you need to execute before any I/O.
Q: What blocks the Node.js event loop? How do you fix it?
Answer: The event loop is single-threaded. Anything that runs synchronously for a long time blocks all other callbacks. Common blockers: CPU-intensive computation (complex JSON parsing, cryptography, image processing, large array operations), synchronous file system calls (fs.readFileSync), synchronous crypto (crypto.pbkdf2Sync).
Fixes: (1) Move CPU-heavy work to Worker Threads — they run on separate OS threads without blocking the event loop. (2) Use async versions of all I/O APIs (fs.readFile not fs.readFileSync). (3) Break heavy computation into chunks with setImmediate() to allow other callbacks to interleave. (4) Offload to a child process or worker service. The key principle: the event loop should only do I/O coordination — never actual number crunching.

Topic 2: Libuv, Thread Pool & Worker Threads

  • [MUST KNOW] Libuv: C library that provides Node's async I/O, thread pool, and event loop implementation. Node.js is not single-threaded at the OS level — libuv uses a thread pool for operations the OS doesn't support natively as async (file system, DNS lookup, crypto).
  • [MUST KNOW] Thread Pool (default 4 threads, max 1024): Used for: fs.* (file I/O), dns.lookup() (not dns.resolve()), crypto (pbkdf2, scrypt, randomBytes), zlib. NOT used for: network I/O (TCP, UDP, HTTP) — these use OS async primitives (epoll/kqueue).
  • [MUST KNOW] Worker Threads (Node 10.5+, stable Node 12+): True OS threads. Share memory via SharedArrayBuffer and Atomics. Each worker has its own V8 instance and event loop. Best for: CPU-intensive tasks (parsing, compression, encryption, ML inference). NOT for: I/O — use async I/O instead.
  • [SHOULD KNOW] Child Process vs Worker Threads: Child process = separate Node.js process, separate memory, communicate via IPC (JSON serialization). More isolation, higher overhead. Worker threads = same process, shared memory possible, lower overhead. Use child process for running separate programs/scripts. Use worker threads for CPU work in the same codebase.
  • [SHOULD KNOW] Clustering: cluster module forks N worker processes (typically = CPU cores). Master distributes connections using round-robin (Linux) or OS-level (Windows). Useful for utilizing all CPU cores on a single machine. PM2 makes this easy in production. Workers can crash and restart independently.
Q: You have a Node.js API that does heavy JSON transformation on each request. It's slow and blocking. How do you fix it?
Answer: JSON transformation is CPU-bound — it blocks the event loop. Options in order of complexity:
1. Worker Threads pool: Create a pool of worker threads (e.g., using worker_threads or a library like piscina). Offload transformation to a worker, get result back via message passing. The event loop is free to handle other requests during transformation.
2. Optimize the transformation itself: Is it actually slow or just poorly written? Profile with --prof flag. Sometimes a better algorithm reduces the need for offloading.
3. Cache the result: If the same input repeatedly produces the same output, cache it in Redis or in-memory LRU cache.
4. Streaming: If the JSON is large, stream the transformation instead of loading everything into memory at once.
I'd start with profiling to confirm the bottleneck, then implement a worker thread pool if the transformation is genuinely CPU-bound.

Topic 3: Streams & Backpressure

  • [MUST KNOW] 4 Stream Types:
    • Readable: Source of data. fs.createReadStream(), HTTP request body, TCP socket.
    • Writable: Destination. fs.createWriteStream(), HTTP response, TCP socket.
    • Duplex: Both readable and writable. TCP socket.
    • Transform: Duplex that modifies data. zlib.createGzip(), crypto.createCipheriv().
  • [MUST KNOW] Why Streams? Memory efficiency. Without streams, reading a 10GB file into memory crashes Node. With streams, process chunk by chunk in ~64KB pieces. Time-to-first-byte is also faster (can start sending before entire file is read).
  • [MUST KNOW] Backpressure: When a writable stream can't consume data as fast as a readable produces it, the buffer fills up. write() returns false when buffer is full. You must pause the readable (readable.pause()) until the writable emits 'drain', then resume. If you ignore backpressure, memory grows unboundedly.
  • [SHOULD KNOW] pipe() vs pipeline(): pipe() handles backpressure automatically but does NOT forward errors — if source errors, destination doesn't close → memory leak. pipeline() (Node 10+) handles backpressure AND forwards errors AND destroys all streams on error. Always use pipeline() in production.
Q: How would you serve a 10GB file download without running out of memory?
Answer: Use streams — never load the entire file into memory. In Node.js: 
const { pipeline } = require('stream/promises');
const fs = require('fs');

app.get('/download/:filename', async (req, res) => {
  const filePath = path.resolve('./files', req.params.filename);
  // Security: validate filePath doesn't escape ./files directory
  
  res.setHeader('Content-Disposition', `attachment; filename="${req.params.filename}"`);
  res.setHeader('Content-Type', 'application/octet-stream');
  
  const readStream = fs.createReadStream(filePath);
  await pipeline(readStream, res); // handles backpressure + error cleanup
});
This reads the file in 64KB chunks and pipes directly to the HTTP response. Backpressure is handled automatically — if the client downloads slowly, the read stream pauses. Memory usage stays constant regardless of file size. For better performance: add Content-Length header (from file stat) and support Range requests for resumable downloads.

Topic 4: Memory Management & Leaks

  • [MUST KNOW] V8 Heap Structure: New Space (young generation, small, frequent GC), Old Space (survived 2+ GC cycles, larger, less frequent GC), Large Object Space (>256KB), Code Space (JIT-compiled code).
  • [MUST KNOW] Common Memory Leaks:
    • Forgotten event listeners: emitter.on('data', handler) without a corresponding removeListener in cleanup. Use emitter.once() for one-time listeners.
    • Global variables / module-level caches: Arrays/Maps that grow forever. Add size limits or TTL-based eviction.
    • Closures holding large scope: A closure keeps its entire scope alive. If a large object is in scope, it won't be GC'd.
    • Timers not cleared: setInterval() without clearInterval() in cleanup.
    • Unbounded Promise chains: If Promises are created faster than resolved and references kept.
  • [SHOULD KNOW] Detecting Leaks: Use node --inspect + Chrome DevTools Heap Snapshot. Take snapshots at time T1 and T2 under load, compare. Objects that grew between snapshots are suspects. process.memoryUsage() for runtime monitoring. clinic.js tool suite for profiling.
  • [BONUS] WeakMap and WeakSet — keys/values are held weakly, GC can collect them. Useful for metadata attached to objects without preventing GC.

Topic 5: Express.js / Middleware Architecture

  • [MUST KNOW] Middleware chain: Express middleware is a pipeline. Each middleware gets (req, res, next). Call next() to pass to next middleware. Call next(error) to pass to error handler. Order matters — middleware runs in declaration order.
  • [MUST KNOW] Error handling middleware: 4 arguments: (err, req, res, next). Must be defined LAST. If you don't call next(err), the error is silently swallowed — this is a common bug.
  • [MUST KNOW] Common middleware pattern: helmet() (security headers), cors(), express.json(), auth middleware, rate limiter middleware, route handlers, error handler.
  • [SHOULD KNOW] async/await with Express: Express doesn't catch async errors by default. Need to wrap async route handlers: either use a custom asyncHandler(fn) wrapper that calls next(err) on rejection, or use Express 5 (which handles it natively). This is a very common bug in Node.js codebases.
// The asyncHandler wrapper pattern — critical to know
const asyncHandler = (fn) => (req, res, next) => {
  Promise.resolve(fn(req, res, next)).catch(next);
};

// Usage:
app.get('/users/:id', asyncHandler(async (req, res) => {
  const user = await User.findById(req.params.id); // if this throws, next(err) is called
  if (!user) return res.status(404).json({ error: 'User not found' });
  res.json(user);
}));

// Error handler (must be defined last, 4 args)
app.use((err, req, res, next) => {
  const status = err.status || 500;
  res.status(status).json({ 
    error: process.env.NODE_ENV === 'production' ? 'Internal error' : err.message 
  });
});

Topic 6: HTTP Internals & Security

  • [MUST KNOW] HTTP/1.1 Keep-Alive: Persistent connection — multiple requests over single TCP connection. Reduces TCP handshake overhead. Default in HTTP/1.1. Connection reuse via connection pool in HTTP clients.
  • [MUST KNOW] HTTP/2: Multiplexing — multiple requests/responses over single connection simultaneously. No head-of-line blocking (unlike HTTP/1.1 pipelining). Header compression (HPACK). Binary protocol. Server push (rarely used in practice). Requires HTTPS.
  • [MUST KNOW] CORS: Browser security policy — prevents JS from making cross-origin requests unless server explicitly allows via Access-Control-Allow-Origin header. Preflight request (OPTIONS) sent first for non-simple requests. Server-side configuration only. CORS does not protect your API from server-to-server calls or curl — only browser JS.
  • [MUST KNOW] HTTPS / TLS Handshake (simplified): Client hello (supported TLS versions, cipher suites) → Server hello (chosen cipher, certificate) → Client verifies certificate against CA → Key exchange (ECDHE for forward secrecy) → Symmetric encryption established. TLS 1.3 reduces handshake from 2 RTT to 1 RTT.
  • [MUST KNOW] Security Headers (via Helmet):
    • Content-Security-Policy: whitelist where scripts/styles can be loaded from. Mitigates XSS.
    • X-Frame-Options: DENY: prevents clickjacking (loading your page in an iframe).
    • X-Content-Type-Options: nosniff: prevents MIME type sniffing.
    • Strict-Transport-Security: forces HTTPS for future requests.
  • [SHOULD KNOW] CSRF (Cross-Site Request Forgery): Attacker tricks logged-in user's browser into making a request to your server. Defense: CSRF tokens (double-submit cookie pattern), SameSite cookie attribute (SameSite=Strict or Lax), verify Origin/Referer header.
Q: Explain how CORS works and what it actually protects against.
Answer: CORS is enforced by browsers to prevent malicious JavaScript on one origin (e.g., evil.com) from making authenticated requests to another origin (e.g., yourbank.com) using the user's cookies. Without CORS, if evil.com loads in a browser where you're logged into yourbank.com, it could silently call yourbank.com API and read your account data.
How it works: The browser sends the request with an Origin header. If it's a "complex" request (non-GET/POST, custom headers, JSON body), the browser first sends a preflight OPTIONS request. The server responds with Access-Control-Allow-Origin, Access-Control-Allow-Methods, etc. If not whitelisted, the browser blocks the response from reaching the JS code.
What CORS does NOT protect against: Server-to-server calls (no browser = no CORS enforcement), curl, Postman, or any non-browser client. CORS is purely a browser safety mechanism. Don't rely on it as your API's security — you still need proper authentication.

Topic 7: REST API Design — Senior Level

  • [MUST KNOW] HTTP Method Semantics: GET (read, idempotent, safe), POST (create, not idempotent), PUT (replace entire resource, idempotent), PATCH (partial update, not necessarily idempotent), DELETE (idempotent). Idempotent = same request multiple times = same result.
  • [MUST KNOW] Status Codes to know cold:
    • 200 OK, 201 Created, 204 No Content (success with no body)
    • 301 Moved Permanently (with Location header), 302 Found (temporary redirect)
    • 304 Not Modified (client has fresh cached version)
    • 400 Bad Request (malformed input), 401 Unauthorized (not authenticated), 403 Forbidden (authenticated but no permission)
    • 404 Not Found, 409 Conflict (e.g., duplicate resource), 422 Unprocessable Entity (validation error)
    • 429 Too Many Requests (rate limited), 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable
  • [MUST KNOW] Pagination: Offset pagination (simple but slow for large offsets — DB scans all rows to skip). Cursor pagination (uses last item's ID/timestamp as cursor — consistent, fast even at page 1000, handles inserts/deletes gracefully). Use cursor for anything with >10k records or real-time data.
  • [SHOULD KNOW] API Versioning: URL versioning (/api/v1/users) — most visible, easiest to route. Header versioning (Accept: application/vnd.api+json;version=1) — cleaner URLs but harder to test. Never break existing clients. Deprecate, then sunset with advance notice.
  • [SHOULD KNOW] Idempotency Keys: Client generates UUID for mutating requests. Server checks if key was already processed → return cached result. Prevents duplicate charges/operations on network retry. Essential for payments.
Q: Design the REST API for a blog platform. What endpoints, what methods, what status codes?
Answer: 
POST   /api/v1/posts          → 201 Created  (create post)
GET    /api/v1/posts          → 200 OK       (list, with cursor pagination)
GET    /api/v1/posts/:id      → 200 / 404    (get single)
PUT    /api/v1/posts/:id      → 200 / 404    (replace post, author only)
PATCH  /api/v1/posts/:id      → 200 / 404    (partial update, author only)
DELETE /api/v1/posts/:id      → 204 / 404    (delete, author only)

POST   /api/v1/posts/:id/comments   → 201    (add comment)
GET    /api/v1/posts/:id/comments   → 200    (list comments)
DELETE /api/v1/comments/:id         → 204    (delete comment)
Key decisions: Nested resources (/posts/:id/comments) for natural ownership. Flat resource for delete (/comments/:id) to avoid needing postId for a simple delete. Always return the created/updated resource in response body — not just 201/200. Include pagination metadata: { data: [...], nextCursor: "xyz", hasMore: true }. Return 403 (not 404) when resource exists but user lacks permission — prevents enumeration attacks. Use 422 for validation errors, not 400 — 400 is for malformed requests, 422 is for semantically invalid data.

Topic 8: Authentication Implementation

// JWT implementation pattern — know this cold
const jwt = require('jsonwebtoken');

// Generate access + refresh token pair
function generateTokenPair(userId) {
  const accessToken = jwt.sign(
    { sub: userId, type: 'access' },
    process.env.JWT_ACCESS_SECRET,
    { expiresIn: '15m' }
  );
  const refreshToken = jwt.sign(
    { sub: userId, type: 'refresh' },
    process.env.JWT_REFRESH_SECRET,
    { expiresIn: '7d' }
  );
  return { accessToken, refreshToken };
}

// Auth middleware
async function authenticate(req, res, next) {
  const authHeader = req.headers.authorization;
  if (!authHeader?.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'No token provided' });
  }
  const token = authHeader.split(' ')[1];
  try {
    const payload = jwt.verify(token, process.env.JWT_ACCESS_SECRET);
    req.user = { id: payload.sub };
    next();
  } catch (err) {
    if (err.name === 'TokenExpiredError') {
      return res.status(401).json({ error: 'Token expired', code: 'TOKEN_EXPIRED' });
    }
    return res.status(401).json({ error: 'Invalid token' });
  }
}

// Refresh token endpoint
app.post('/auth/refresh', async (req, res) => {
  const { refreshToken } = req.body; // or from httpOnly cookie
  try {
    const payload = jwt.verify(refreshToken, process.env.JWT_REFRESH_SECRET);
    // Check if refresh token is still valid in DB (for revocation)
    const storedToken = await RefreshToken.findOne({ 
      token: refreshToken, 
      userId: payload.sub, 
      revoked: false 
    });
    if (!storedToken) return res.status(401).json({ error: 'Invalid refresh token' });
    
    // Rotation: revoke old, issue new
    await storedToken.update({ revoked: true });
    const newPair = generateTokenPair(payload.sub);
    await RefreshToken.create({ token: newPair.refreshToken, userId: payload.sub });
    
    res.json(newPair);
  } catch {
    res.status(401).json({ error: 'Invalid refresh token' });
  }
});

Topic 9: Testing Patterns

  • [MUST KNOW] Test Pyramid: Unit tests (fast, isolated, many) → Integration tests (DB/external calls, fewer) → E2E tests (slow, brittle, fewest). Cost and feedback speed inverts as you go up the pyramid.
  • [MUST KNOW] What to unit test in Node: Business logic functions, validators, transformers, utility functions. Inject dependencies — don't let functions reach out to DB/external services directly.
  • [MUST KNOW] Mocking strategies: Jest's jest.mock() for module replacement. jest.spyOn() to monitor/override specific methods. Manual dependency injection — pass DB/service as parameter instead of importing directly (more testable, no mocking needed).
  • [SHOULD KNOW] Testing async code: Always return promises or use async/await in tests. Use jest.fakeTimers() for testing setTimeout/setInterval logic. Supertest for HTTP endpoint testing — starts actual Express server, makes real HTTP calls.
Q: How do you test a service function that calls an external payment API?
Answer: You don't want real payment API calls in unit tests. I'd use dependency injection — pass the payment client as a parameter to the service function (or inject it via constructor in a class). In tests, inject a mock that returns predetermined responses.
For integration tests where I want to test the actual HTTP layer: use nock or msw (Mock Service Worker) to intercept HTTP calls at the network level and return mock responses. Never make real external API calls in automated tests — they're slow, flaky, and can have side effects (real charges). The test should verify your service handles success, failure, and timeout responses correctly.

Q: A user reports they can see other users' orders by changing the order ID in the URL. What is this vulnerability and how do you fix it?
Answer: This is Insecure Direct Object Reference (IDOR) — a type of Broken Object-Level Authorization (BOLA). The API is fetching the resource by ID without verifying the requester owns it.
Fix: Always scope queries to the authenticated user: 
// VULNERABLE:
const order = await Order.findById(req.params.id);

// SECURE:
const order = await Order.findOne({ 
  _id: req.params.id, 
  userId: req.user.id  // ensures the order belongs to this user
});
if (!order) return res.status(404).json({ error: 'Order not found' });
// Return 404 not 403 — don't reveal that the resource exists
Beyond fixing this specific endpoint: add an authorization middleware layer that checks ownership for all resource-level operations. Write tests specifically for "user A cannot access user B's resources."
