Priority 1 — System Design

Weight: Highest for international remote | Medium for Pakistan | Estimated prep time: 28 hrs

Depth Guide for System Design
[MUST KNOW] — Core concepts. If you can't explain these clearly, you fail the round.
[SHOULD KNOW] — Shows senior thinking. Differentiates you from a mid-level candidate.
[BONUS] — Only if you have extra time or the role specifically demands it. Mentioning awareness is enough.
The System Design Interview Framework (use every time):
1. Clarify Requirements (2–3 min): Functional requirements. Non-functional (scale, latency, availability). Constraints. Ask, don't assume.
2. Back-of-Envelope Estimation (2–3 min): QPS (queries per second), storage needed, bandwidth. Shows engineering mindset.
3. High-Level Design (5–7 min): Box diagram. Core components. Happy path.
4. Deep Dive (15–20 min): Pick 2–3 components and go deep. Let the interviewer guide which.
5. Bottlenecks + Trade-offs (5 min): What breaks first? How do you scale it? What did you sacrifice?
Never jump straight to a solution. Always ask first.

Topic 1: Scalability Fundamentals

Core Concepts

  • [MUST KNOW] Horizontal vs Vertical scaling: Vertical = bigger machine (CPU/RAM limit, single point of failure). Horizontal = more machines (needs stateless design, load balancer, distributed state). Real systems go horizontal.
  • [MUST KNOW] Stateless design: No session data on server. State lives in DB, Redis, or JWT. Every server can handle any request. Prerequisite for horizontal scaling.
  • [MUST KNOW] CAP Theorem: In a network partition, you must choose: Consistency (every read gets latest write) OR Availability (every request gets a response). You cannot have both. CP systems: HBase, ZooKeeper. AP systems: Cassandra, DynamoDB, CouchDB. CA systems: don't exist in distributed systems with partitions.
  • [SHOULD KNOW] PACELC: Extension of CAP. Even without partitions: trade-off between Latency and Consistency. More relevant in practice.
  • [SHOULD KNOW] Eventual consistency: Nodes will converge to the same state given enough time and no new writes. DNS is a real-world example. Use when strong consistency is too expensive.
  • [BONUS] CRDT (Conflict-free Replicated Data Types) — how systems like Google Docs resolve concurrent edits without conflicts.
Q: What's the difference between horizontal and vertical scaling? When would you choose each?
Answer: Vertical scaling adds more resources to a single server (CPU, RAM, faster storage). It's simple — no code changes needed — but has a hard ceiling and is a single point of failure. Horizontal scaling adds more servers running the same service. It requires stateless design (no in-memory session state; sessions in Redis, state in DB) and a load balancer in front. Vertical is the right first step when you need a quick win and the bottleneck is a single server. Once you hit the vertical ceiling or need high availability, you go horizontal. For a database, vertical scaling (more RAM for buffer pool, faster SSDs) often gets you farther than people expect before you need sharding.
Q: Explain CAP theorem and give a real example.
Answer: In a distributed system that experiences a network partition (nodes can't communicate), you must choose between Consistency — every read reflects the most recent write — or Availability — every request receives a response, even if it might be stale. You cannot guarantee both simultaneously. A banking system typically chooses CP: it's better to return an error than to show an incorrect balance. A shopping cart or social media feed typically chooses AP: showing a slightly stale count is acceptable if the system stays up. The real insight is that this is a design decision, not a flaw. You pick your trade-off based on your domain requirements.

Topic 2: Load Balancing

Core Concepts

  • [MUST KNOW] L4 vs L7 Load Balancing: L4 (Transport Layer) routes based on IP/TCP. Fast, can't inspect content. L7 (Application Layer) routes based on HTTP headers, URL, cookies. Can do content-based routing, SSL termination, sticky sessions. Nginx, HAProxy, AWS ALB are L7.
  • [MUST KNOW] Algorithms: Round Robin (equal distribution), Weighted Round Robin (different server capacities), Least Connections (route to server with fewest active connections — better than round robin for variable request durations), IP Hash (same client always hits same server — for sticky sessions), Consistent Hashing (used for cache servers — minimizes redistribution when nodes change).
  • [MUST KNOW] Health checks: Active (LB pings servers periodically) vs Passive (LB monitors real traffic for failures). When a server fails health check, traffic is rerouted.
  • [SHOULD KNOW] Session Persistence (Sticky Sessions): Same user always routed to same server. Needed if session state is local. Breaks horizontal scaling benefit. Prefer stateless + Redis sessions instead.
  • [SHOULD KNOW] Consistent Hashing: Hash function maps servers to a ring. Each request maps to nearest server on ring. When adding/removing a server, only ~1/N requests remapped (vs all requests with simple modulo). Used by CDNs, distributed caches, databases.
Q: You have a Node.js app with multiple instances. User session breaks when requests hit different servers. How do you fix this?
Answer: The root cause is server-side session state — sessions stored in memory on individual servers. Two solutions: (1) Sticky sessions at the load balancer — route each user to the same server. Simple but hurts scalability and creates uneven load. If that server dies, session is lost. (2) Externalized sessions — store session data in Redis (or a shared store). Every server can read/write sessions for any user. This is the correct solution for horizontal scalability. I'd choose Redis with express-session or a JWT-based approach so the session data is in the token itself, removing the shared store entirely for stateless services.

Topic 3: Caching

Cache Strategies

  • [MUST KNOW] Cache-aside (Lazy Loading): App checks cache first. On miss, reads from DB, writes to cache, returns data. Cache only contains requested data. Risk: cold start, stale data on DB update. Most common pattern.
  • [MUST KNOW] Write-through: Every DB write also writes to cache synchronously. Cache always fresh. Risk: cache grows large with data never read. Write latency increases.
  • [MUST KNOW] Write-behind (Write-back): Write to cache immediately, async write to DB. Low write latency. Risk: data loss if cache crashes before DB write.
  • [MUST KNOW] Cache Invalidation: The hardest problem. TTL-based (simple, may serve stale). Event-driven invalidation (explicit delete on change — precise but complex). Tag-based invalidation (group related keys, invalidate group). "There are only two hard problems in CS: cache invalidation and naming things."
  • [MUST KNOW] Eviction Policies: LRU (Least Recently Used — most common), LFU (Least Frequently Used — better for skewed access patterns), TTL expiry, Random.
  • [SHOULD KNOW] Cache stampede / Thundering Herd: Many requests hit a cache miss simultaneously, all go to DB. Solutions: probabilistic early expiration, mutex/lock on cache miss, background refresh.
  • [SHOULD KNOW] CDN Caching: Static assets (images, CSS, JS) served from edge nodes close to users. Cache-Control headers control CDN behavior. Cache-Control: max-age=31536000, immutable for versioned assets.
  • [BONUS] Bloom filters for "definitely not in cache" checks to avoid DB lookups for non-existent keys (cache penetration attack mitigation).
Q: How would you cache user profile data that changes infrequently but must be consistent within 1 minute?
Answer: I'd use cache-aside with a TTL of 60 seconds. On read: check Redis first, if miss read from DB and cache with 60s TTL. On user profile update: write to DB and immediately invalidate (delete) the cache key. This gives you: fresh data within 60 seconds of any change even without explicit invalidation, and immediate freshness for the updated user if you do explicit invalidation. The 60s TTL is a safety net for edge cases (e.g., failed invalidation). Key format: user:profile:{userId}. I wouldn't use write-through here because profile writes are infrequent — write-through wastes resources caching data that may never be re-read.

Topic 4: Database Scaling

Core Concepts

  • [MUST KNOW] Read Replicas: Primary handles writes. Replicas handle reads. Replication lag means reads might be slightly stale. Good for read-heavy workloads (80%+ reads is common). Route reports, analytics, non-critical reads to replicas.
  • [MUST KNOW] Database Sharding: Horizontal partitioning across multiple DB instances. Each shard holds a subset of data. Shard key determines which shard a record goes to. Enables horizontal scaling of writes. Downsides: cross-shard joins are expensive/impossible, re-sharding is painful, application complexity increases significantly.
  • [MUST KNOW] Sharding Strategies: Range sharding (e.g., users A–M on shard 1, N–Z on shard 2) — simple but hotspots possible. Hash sharding (hash(userId) % N) — even distribution but no range queries. Directory/lookup sharding — flexible but lookup table is a bottleneck. Geographic sharding — data in same region as users.
  • [SHOULD KNOW] CQRS (Command Query Responsibility Segregation): Separate models (and often stores) for reads and writes. Write side has normalized schema. Read side has denormalized, query-optimized projections. Eliminates read/write contention. Complex to implement. Often combined with Event Sourcing.
  • [SHOULD KNOW] Connection Pooling: DB connections are expensive to create. Pool maintains a fixed set of open connections reused across requests. Prevents "too many connections" errors. PgBouncer for PostgreSQL. Mongoose handles pooling for MongoDB. Configure pool size based on DB max_connections and concurrent requests.
  • [BONUS] Vitess (MySQL sharding), CockroachDB (distributed SQL), NewSQL databases.
Q: Our read-heavy API is slow because the DB is overloaded. Walk me through how you'd scale it.
Answer: I'd scale in layers, each buying significant relief before the next:
1. Query optimization first — Add missing indexes, fix N+1 queries, optimize slow queries (EXPLAIN). This often gives 10x improvement with zero infrastructure change.
2. Application-level caching — Add Redis cache-aside for frequently read, rarely changed data (user profiles, config, product catalog). Aim for 80%+ cache hit rate.
3. Read replicas — Spin up 1–2 replicas, route all read-only queries there. Writes still go to primary. This doubles effective read capacity immediately.
4. Connection pooling — If not already using PgBouncer or equivalent, add it. Prevents connection storms.
5. Sharding — Only if the above don't suffice. Pick a shard key that distributes evenly and matches your primary access patterns. This is a last resort due to operational complexity.
I'd always measure first: is the bottleneck CPU, I/O, locks, or network? The fix depends on the bottleneck.

Topic 5: Message Queues & Async Processing

Core Concepts

  • [MUST KNOW] Why queues? Decoupling (producer/consumer can evolve independently), buffering (absorb traffic spikes), async processing (don't block user on slow operations like email sending, PDF generation, video processing), reliability (if consumer is down, messages wait).
  • [MUST KNOW] Delivery Guarantees:
    • At-most-once: fire and forget. Fast but messages can be lost. Use for analytics, metrics.
    • At-least-once: messages redelivered if not acknowledged. Consumer must be idempotent. Use for emails, payments, notifications.
    • Exactly-once: hardest. Requires idempotent producers + transactional consumers. Kafka Transactions support this.
  • [MUST KNOW] Kafka vs RabbitMQ: Kafka is a distributed event log — designed for high throughput, replay, event sourcing, stream processing. Messages persist. Multiple consumer groups can read the same topic. RabbitMQ is a traditional message broker — designed for task queues, routing, dead-letter queues. Messages deleted after consumption. Choose Kafka when you need replay or high throughput (>100k msg/sec). Choose RabbitMQ for complex routing, lower latency, lower volume.
  • [SHOULD KNOW] Dead Letter Queue (DLQ): Where failed/unprocessable messages go after max retries. Essential for production systems. Allows investigation without blocking the main queue.
  • [SHOULD KNOW] Idempotency: Processing the same message twice gives the same result as processing it once. Required for at-least-once delivery. Implement via idempotency keys, checking if work is already done before doing it.
  • [BONUS] Kafka internals: partitions, consumer groups, offset management, partition leadership election (Raft-based in KRaft mode).
Q: When would you NOT use a message queue?
Answer: Queues add complexity — another service to operate, monitor, scale, and handle failures for. Avoid them when: (1) The operation is fast enough to do synchronously without impacting UX — don't queue a DB write that takes 5ms. (2) You need the result immediately to respond to the user — queues are for fire-and-forget or async flows. (3) Your volume is low and a cron job or in-process background job would suffice. (4) You don't have the operational maturity to run Kafka reliably — a simpler tool (Bull queue with Redis, pg-boss with PostgreSQL) may be better. Over-engineering with Kafka when BullMQ would do is a common mistake I've seen in small teams.

Topic 6: Rate Limiting

Algorithms

  • [MUST KNOW] Token Bucket: Bucket holds up to N tokens. Tokens refill at a fixed rate (R per second). Each request consumes 1 token. If bucket is empty, request is rejected. Allows bursting up to N. Most flexible algorithm. Redis INCR + TTL or Lua scripts implement this efficiently.
  • [MUST KNOW] Leaky Bucket: Requests enter a queue (bucket). Queue drains at a fixed rate. Excess requests overflow (rejected). Produces smooth output rate. No bursting allowed. Good for downstream services that can't handle bursts.
  • [MUST KNOW] Fixed Window Counter: Count requests per time window (e.g., per minute). Simple but has boundary spike problem — 100 requests at end of window 1 + 100 requests at start of window 2 = 200 requests in 2-second span.
  • [SHOULD KNOW] Sliding Window Log: Store timestamp of each request. Count requests in last N seconds. Precise but memory-intensive (stores every request timestamp).
  • [SHOULD KNOW] Sliding Window Counter: Hybrid — combines fixed window counters with weighting. Approximates sliding window. Low memory, close to sliding window accuracy. Redis sorted sets implement this well.
  • [SHOULD KNOW] Distributed Rate Limiting: Single Redis instance as shared counter. All API gateway nodes read/increment the same counter. Lua scripts for atomic check-and-increment. Watch out for Redis latency adding to API response time.
Q: Design a rate limiter for an API that allows 100 requests per user per minute. How does it work at scale with multiple API servers?
Answer: I'd use a sliding window counter backed by Redis.
Data structure: Redis sorted set per user — key: rate:userId, score: timestamp in milliseconds, member: unique request ID.
Algorithm on each request:
1. Remove entries older than 60 seconds: ZREMRANGEBYSCORE rate:userId 0 (now-60000)
2. Count current entries: ZCARD rate:userId
3. If count >= 100: reject with 429 Too Many Requests, include Retry-After header
4. Otherwise: add entry ZADD rate:userId now requestId and set TTL: EXPIRE rate:userId 60
5. Steps 1–4 wrapped in a Lua script for atomicity
At scale: All API servers point to the same Redis cluster. Redis handles the distributed counting. If Redis becomes a bottleneck, consider Redis Cluster with user sharding. Rate limits are per-user, so consistent hashing on userId distributes load evenly across Redis nodes.
Trade-offs: Redis adds ~1ms latency per request. For extreme scale, local approximate counters with periodic Redis sync reduce Redis load at the cost of some accuracy.

Topic 7: API Gateway & Reverse Proxy

This maps directly to your Go project — own this topic completely.

Core Concepts

  • [MUST KNOW] Reverse Proxy vs Forward Proxy: Forward proxy sits in front of clients (VPN, corporate proxy — clients use it to reach internet). Reverse proxy sits in front of servers (clients think they're talking to a single server, actually routing to multiple backends). Nginx, HAProxy, Envoy are reverse proxies.
  • [MUST KNOW] API Gateway = Reverse Proxy + API management features: Rate limiting, auth (JWT verification, API keys), request/response transformation, logging, tracing, circuit breaking, load balancing, SSL termination, protocol translation.
  • [MUST KNOW] Request Lifecycle through a Gateway: Client sends request → DNS resolution → TLS handshake → Gateway receives → Auth middleware (validate JWT/API key) → Rate limit check → Route matching → Request transformation → Forward to upstream service → Receive response → Response transformation → Return to client. Logging + tracing at each step.
  • [SHOULD KNOW] Circuit Breaker Pattern: Prevent cascading failures. States: Closed (normal), Open (stop sending, return fast failure), Half-Open (test if service recovered). Thresholds: failure rate % or consecutive failures. Libraries: resilience4j (Java), Hystrix (deprecated), polly (.NET), your own in Go.
  • [SHOULD KNOW] SSL Termination at Gateway: HTTPS from client to gateway. HTTP or internal HTTPS between gateway and services. Reduces TLS overhead on backend services. Certificates managed at gateway only.
  • [BONUS] Service mesh (Istio, Linkerd) — moves gateway concerns (auth, rate limiting, tracing) into a sidecar proxy next to each service. Removes language-specific library dependencies.
Q: Walk me through the request lifecycle in your reverse proxy. What design decisions did you make and why?
Answer Framework (adapt to your actual implementation):
"A request comes in over HTTP/HTTPS. The first thing my proxy does is [TLS termination / raw TCP accept]. It then parses the request headers to determine routing — I use [config-file-based routing / path prefix matching].
My middleware chain processes in order: (1) Request logging — log method, path, client IP, timestamp. (2) Auth middleware — extract and verify JWT, attach user context using Go's context package. (3) Rate limiter — I implemented a token bucket backed by [in-memory map / Redis]. Key decision: I chose token bucket over leaky bucket because it allows short bursts while still enforcing average limits. (4) Route matching — longest prefix wins. (5) Upstream forwarding — I use Go's httputil.ReverseProxy as the base with custom error handling. I set reasonable timeouts (dial: 5s, response header: 10s, total: 30s) to prevent slow upstream services from exhausting goroutines.
Key invariant I maintain: if auth fails, rate limiter is never even reached (fail fast). If upstream is unavailable, I return a structured JSON error with a 502. I don't expose upstream error details to the client — that's an important security boundary.
Trade-off I made: I chose simplicity over maximum performance. Using httputil.ReverseProxy means I'm not doing zero-copy streaming, but it's much easier to maintain. For a production system at scale, I'd consider a lower-level implementation."

Topic 8: Authentication at Scale

Core Concepts

  • [MUST KNOW] JWT (JSON Web Token): header.payload.signature. Header: algorithm (RS256, HS256). Payload: claims (sub, exp, iat, custom). Signature: HMAC-SHA256 or RSA-SHA256. Stateless — server needs only the secret/public key to verify. No DB lookup per request. Downside: can't revoke before expiry without a denylist.
  • [MUST KNOW] Access + Refresh Token Pattern: Short-lived access token (15 min) — sent with every request, stored in memory (never localStorage). Long-lived refresh token (7–30 days) — stored in httpOnly cookie, used only to get new access tokens. On access token expiry, use refresh token to get a new pair. On logout, invalidate refresh token in DB.
  • [MUST KNOW] OAuth2 Flows:
    • Authorization Code + PKCE: web apps, mobile apps. User-facing login. Most secure.
    • Client Credentials: service-to-service, no user involved. Machine auth.
    • Implicit: deprecated. Don't use.
    • Device Code: TV/CLI apps where no browser redirect is possible.
  • [SHOULD KNOW] Token Storage: Access tokens: in-memory (JS variable) — XSS can't steal, tab refresh loses it. Refresh tokens: httpOnly + Secure + SameSite=Strict cookie — not accessible to JS, sent only over HTTPS, CSRF-resistant. Never localStorage for tokens.
  • [SHOULD KNOW] Refresh Token Rotation: Each use of a refresh token issues a new refresh token and invalidates the old one. If a stolen refresh token is used, the legitimate user's next refresh will fail (old token already invalidated), signaling a breach. Invalidate the entire token family (all refresh tokens for that user/session).
  • [BONUS] PASETO (Platform-Agnostic Security Tokens) as a safer alternative to JWT. OpenID Connect (OIDC) as identity layer on top of OAuth2.
Q: JWT vs Session tokens — when would you choose each?
Answer: Sessions (server-side, stored in Redis/DB): easy revocation (delete session record), flexible payload updates, small cookie, but requires shared session store across servers — adds latency and operational complexity. JWT: stateless verification, no shared store, good for microservices (each service verifies independently), but can't revoke a valid token before expiry without a denylist (which brings back the shared store problem).
My decision rule: Use JWTs for service-to-service auth and scenarios where revocation isn't critical or access tokens are short-lived (<15 min). Use sessions for user-facing auth where you need immediate revocation (admin banning a user, forced logout). In practice, many systems use a hybrid: JWT access tokens (short-lived, stateless) + database-tracked refresh tokens (long-lived, revocable). This gives stateless performance with revocation capability.

System Design Practice Problems

For each problem: attempt solo first (15–20 min), then study the framework. Use the 5-step framework every time.

Problem 1: Design a URL Shortener (bit.ly)

Requirements to clarify: How many URLs shortened/day? Read vs write ratio? Custom aliases? Analytics needed? URL expiry?
Estimates (100M URLs/day): 100M URLs/day = ~1,200 writes/sec. Read:Write = 100:1 = 120,000 reads/sec. Storage: 100M × 500 bytes = 50 GB/day.
  • Core Flow: User submits long URL → generate 7-char alphanumeric code (base62: 62^7 = 3.5 trillion unique codes) → store mapping in DB → return short URL. On redirect: lookup code → return 301/302 redirect.
  • 301 vs 302: 301 (permanent) — browser caches, reduces server load but can't track subsequent clicks. 302 (temporary) — server always hit, allows analytics. Choose based on whether analytics matter.
  • Hash generation: MD5/SHA256 → take first 7 chars → collision risk → check DB → regenerate. Or: use a distributed ID generator (Snowflake IDs) → encode as base62. Or: counter in DB + base62 encoding (simple but counter is a bottleneck).
  • DB choice: Key-value lookup — Redis for hot URLs (cache-aside). Cassandra/DynamoDB for the full mapping table (write-heavy, key-value access pattern fits perfectly). Or PostgreSQL for smaller scale.
  • Scaling: Cache-aside with Redis (top 20% of URLs are 80% of traffic — Pareto). Multiple read replicas. CDN for geographic distribution.
  • Bottleneck: Write path at extreme scale. Solution: async writes with a queue, accept eventual consistency on analytics.

Problem 2: Design a Rate Limiter Service

(See Topic 6 above — you already have the answer. Now design it as a standalone service.)

  • As a standalone service: API servers call rate limiter service before processing. Adds ~1–2ms latency. Rate limiter uses Redis cluster for distributed counters.
  • Config: Rules stored in DB/config (userId → limit, apiKey → limit, IP → limit, endpoint → limit). Rules cached in rate limiter service memory, refreshed every 30s.
  • Headers to return: X-RateLimit-Limit: 100, X-RateLimit-Remaining: 45, X-RateLimit-Reset: 1720000000, Retry-After: 30.
  • Failure mode: If rate limiter service is unavailable — fail open (allow traffic) or fail closed (block traffic). Fail open is usually correct to avoid taking down the entire API.

Problem 3: Design a Notification System

  • Channels: Push (APNs/FCM), Email (SES/SendGrid), SMS (Twilio), In-app (WebSocket/SSE).
  • Core Flow: Event triggers notification → Notification Service creates notification record → routes to channel-specific workers via message queue → workers call third-party APIs → update delivery status.
  • Queue per channel: Each channel has own queue. Email queue slow (rate limited by provider) doesn't block push notifications.
  • Retry logic: Exponential backoff. After max retries → DLQ → alert ops team.
  • User preferences: DB table: userId, channel, enabled, frequency_limit (max 5 emails/day). Check before enqueuing.
  • Deduplication: Idempotency key on notification. If same event triggers multiple notifications, deduplicate by event_id.
  • Template service: Separate service renders notification content. Parameterized templates. Localization.

Problem 4: Design a File Upload Service (like S3)

  • Flow: Client requests presigned upload URL from API → API generates presigned S3 URL (15 min expiry) → Client uploads directly to S3 (bypass your servers) → S3 triggers event on upload complete → your service updates DB record with file metadata.
  • Why presigned URLs: Upload doesn't go through your servers — saves bandwidth, CPU, eliminates single point of failure for upload path.
  • Large files (multipart upload): Split into 5MB+ parts. Upload parts in parallel. S3 completes multipart upload. Resume interrupted uploads by tracking uploaded parts.
  • Security: Validate file type (MIME, magic bytes — not just extension). Scan for malware (ClamAV or AWS GuardDuty). Store in private S3, serve via signed URLs with short expiry. Never serve user-uploaded files from your API domain (XSS risk).
  • Metadata DB: fileId, userId, originalName, s3Key, contentType, size, uploadStatus (pending/complete/failed), createdAt.

Problem 5: Design a Real-Time Chat Application

  • Real-time transport: WebSockets — full-duplex, low latency. SSE — server push only, simpler for one-directional. Long polling — fallback. For chat: WebSockets.
  • Architecture: Chat servers maintain WebSocket connections. Problem: user A is on server 1, user B is on server 2. How does A's message reach B?
  • Solution — Pub/Sub: Each user subscribes to their own channel in Redis Pub/Sub (or Kafka). When A sends a message: save to DB + publish to B's channel. All chat servers subscribe to all channels. B's server receives from Redis and pushes to B's WebSocket.
  • Message storage: Cassandra (time-series access pattern, high write throughput) with partition key = conversationId, clustering key = timestamp.
  • Presence system: Heartbeat every 5s. Store last_seen in Redis (sorted set by timestamp). "Online" = last_seen within 10s.
  • Message ordering: Logical timestamps or Lamport clocks. Don't rely on server timestamps (clock skew).
