Goroutines and Channels

  • [MUST KNOW] Goroutine: Lightweight concurrent function — not an OS thread. Go runtime multiplexes thousands of goroutines onto a small number of OS threads. Create with go func(). Goroutines start with ~2–8KB stack (vs OS thread's 1MB+) — you can run millions concurrently without exhausting memory.
  • [MUST KNOW] Channel: Typed conduit for communicating between goroutines. Buffered vs unbuffered. Send: ch <- value. Receive: value := <-ch. Unbuffered: sender blocks until receiver is ready (synchronization point). Buffered: sender only blocks when buffer is full.
  • [MUST KNOW] select statement: Like switch for channels — waits for the first ready channel. Used for timeouts, cancellation, multiplexing multiple channels.
// Worker pool pattern — essential for a proxy's request handling
func workerPool(jobs <-chan Job, results chan<- Result, numWorkers int) {
    var wg sync.WaitGroup
    for i := 0; i < numWorkers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for job := range jobs { // range on channel — exits when channel closed
                results <- processJob(job)
            }
        }()
    }
    go func() {
        wg.Wait()
        close(results)
    }()
}

// Context propagation — critical for cancellation in proxy
func forwardRequest(ctx context.Context, req *http.Request, upstream string) (*http.Response, error) {
    outReq, err := http.NewRequestWithContext(ctx, req.Method, upstream+req.URL.Path, req.Body)
    if err != nil {
        return nil, err
    }
    // Copy headers
    for k, v := range req.Header {
        outReq.Header[k] = v
    }
    client := &http.Client{Timeout: 30 * time.Second}
    return client.Do(outReq)
}

// select for timeout + cancellation
func doWithTimeout(ctx context.Context, work func() error) error {
    done := make(chan error, 1)
    go func() { done <- work() }()
    select {
    case err := <-done:
        return err
    case <-ctx.Done():
        return ctx.Err() // context cancelled or deadline exceeded
    }
}
  • [MUST KNOW] sync.Mutex vs channel: Mutex for protecting shared state (counter, map). Channel for communication between goroutines and signaling. Rule of thumb: "use channels to share memory by communicating" — but mutex is fine for simple shared state protection.
  • [MUST KNOW] Context package: Carries deadlines, cancellation signals, and request-scoped values across API boundaries. context.WithTimeout(parent, duration), context.WithCancel(parent). Always propagate context through your call chain. Essential in a proxy — if client disconnects, cancel the upstream request to avoid wasting resources.
  • [SHOULD KNOW] sync.WaitGroup: Wait for a collection of goroutines to finish. wg.Add(n), wg.Done() in goroutine, wg.Wait() to block until all done. Used in graceful shutdown: wait for in-flight requests before stopping.
  • [SHOULD KNOW] Data races: Concurrent access to shared memory without synchronization. go test -race flag detects them. Common in proxy when multiple goroutines read/write a shared map (route table, rate limit counters). Fix with sync.RWMutex (multiple concurrent readers, exclusive write) or sync.Map.

5 Technical Decisions Worth Discussing

For each: know the decision, the alternatives you considered, and why you chose what you did.

Decision 1: Middleware Chain Design

Decision: Implemented middleware as Go function wrappers (func(http.Handler) http.Handler) rather than a framework like Gin or Chi.
Why: Wanted to understand the underlying net/http request handling. The standard library pattern (Handler interface + HandlerFunc adapter) is clean and composable. Each middleware is independently testable — I can unit test the auth middleware by passing a mock next handler and verify it returns 401 for invalid tokens without touching any routing logic.
Trade-off: Less ergonomic than Gin — no path params extraction out of the box, no automatic JSON binding. For a production product, I'd use Chi (minimal, stdlib-compatible router). For this learning project, building it manually was the point.

Decision 2: Rate Limiting — In-Memory vs Redis-Backed

Decision: Used an in-memory token bucket (sync.Map of [key → tokenBucket struct]) rather than Redis.
Why: For a single-instance proxy, in-memory is lower latency (~100ns vs ~1ms for Redis round-trip) and no external dependency. The bucket struct has a mutex for thread-safe access. I use sync.Mutex rather than sync.RWMutex because rate limit updates are nearly always writes.
Trade-off: Doesn't work correctly with multiple proxy instances — each instance has its own in-memory counter. If you run 3 proxy replicas, a user can make 3× the rate limit. For a distributed production deployment, you'd need Redis with Lua scripts for atomic check-and-decrement, or a dedicated rate limit service.
Invariant I maintain: The rate limiter middleware runs after auth — you can't exhaust rate limits without a valid API key. This prevents unauthenticated users from consuming rate limit counters.

Decision 3: Auth Boundary and JWT Verification

Decision: The proxy verifies JWTs and only forwards the user's extracted claims (user ID, roles) to upstream services — never the raw JWT.
Why: This is an important security boundary. Upstream services should trust the proxy's assertion that "this is user 123 with role admin" rather than verify JWTs themselves. This means: (1) JWT verification logic lives in one place — the proxy. If the signing key changes, I update one service. (2) Upstream services are simpler — they just read an X-User-Id header. (3) Internal services don't need secret key material to verify tokens.
Trade-off: Creates a trust boundary — upstream services must fully trust the proxy. If the proxy is compromised, all services are compromised. For internal networks this is acceptable; for zero-trust architectures you'd verify tokens at each service too.

Decision 4: Connection Timeouts

Decision: Set explicit timeouts at multiple levels: dial timeout (5s), response header timeout (10s), total request timeout (30s), and idle connection timeout.
Why: Without timeouts, a slow or hung upstream service holds a goroutine open indefinitely. Under load, this exhausts the goroutine pool. Each timeout layer catches different failure modes: dial timeout catches unreachable services, response header timeout catches services that accept the connection but never respond, total timeout catches services that start responding but are extremely slow.
Practical impact: With no timeouts, a 30-second upstream delay would occupy 30 goroutines per second of incoming traffic. With timeouts, those goroutines are freed after 30s maximum, preventing unbounded growth.

Decision 5: Graceful Shutdown

Decision: Implemented graceful shutdown using Go's server.Shutdown() with a context timeout and signal handling.
Why: Hard stopping an HTTP server mid-request drops in-flight requests — users get connection reset errors. Graceful shutdown: (1) Stop accepting new connections immediately. (2) Wait for in-flight requests to complete (up to a timeout). (3) Then exit. This is essential for zero-downtime deployments in a containerized environment.
Implementation: Listen for SIGTERM and SIGINT signals in a goroutine. On signal: call server.Shutdown(ctx) with a 30s timeout. Existing requests complete; new requests get refused. After all requests finish (or timeout), process exits with code 0.

Part 3: Go vs Node.js — Be Ready to Compare

Q: Why did you choose Go over Node.js for this project?
Answer: Node.js would have been more productive for a quick prototype — I know the ecosystem better. I chose Go specifically to learn its concurrency model, which is genuinely different from Node's async/await pattern. Go's approach (goroutines + channels + explicit context cancellation) is a better mental model for infrastructure code where you have many concurrent requests, need fine-grained timeout control, and want the compiler to catch concurrency issues at compile time through type safety.
For a production reverse proxy, Go is also the right tool: lower memory per connection (goroutine vs V8 + Node event loop overhead), single static binary deployment (no npm, no node_modules), and the standard library's net/http is production-quality. Nginx, Envoy, Caddy, and Traefik are all written in Go/C for these reasons.
That said, for an API service with business logic, database calls, and complex data transformations, Node.js + TypeScript is fully competitive and I'd be comfortable choosing either based on team expertise.

The "Why Go for Distributed Systems" Talking Points

  • Goroutines are cheap: You can have 100,000+ goroutines in a single process. OS threads (what Node.js worker threads map to) are limited to thousands. This makes Go natural for proxies and gateways that need to maintain many concurrent connections.
  • Built-in race detector: go test -race and go run -race detect data races at runtime. Critical for concurrent programs.
  • Static binary: Compile to a single binary with all dependencies bundled. No runtime dependency management. Docker images are small. Startup is instant.
  • Standard library: net/http, crypto/tls, encoding/json — all production-quality and part of the stdlib. Nginx + a Go HTTP server have comparable throughput.
  • Explicit error handling: No hidden exceptions. Every function that can fail returns an error. You're forced to handle or propagate it. This is verbose but makes error paths explicit and auditable.
Depth Stop for Go: You need enough to own your project narrative and answer "why Go" credibly. You do NOT need: deep Go runtime internals (GMP scheduler, garbage collector generations), cgo, unsafe package, reflection API. If asked about any of these, it's fine to say "I haven't needed to go that deep yet, but I know the concept is [brief answer]."
