Topic 1: React Internals — Virtual DOM & Reconciliation

Virtual DOM

  • [MUST KNOW] What it is: A lightweight JavaScript object representation of the real DOM. React maintains a tree of these objects in memory. When state changes, React creates a new virtual DOM tree and compares it with the previous one (diffing). Only the actual differences are applied to the real DOM. Real DOM manipulation is slow — batching changes through virtual DOM makes React fast.
  • [MUST KNOW] Why it exists: Directly manipulating the real DOM on every state change would be O(nodes in DOM) and cause unnecessary reflows/repaints. Virtual DOM lets React batch and optimize updates.

Reconciliation (React Fiber)

  • [MUST KNOW] Diffing algorithm: React's reconciliation makes two assumptions that allow O(n) comparison instead of O(n³): (1) Elements of different types produce different trees — React destroys old tree and builds new. (2) Key prop lets React identify which items in a list changed/moved/added — without keys, React can only tell something changed, not what.
  • [MUST KNOW] Why keys matter: Without keys, React diffs a list by position. If you insert a new item at the top of a list, React thinks every item changed (position shift). With stable keys (item ID, not array index), React knows only 1 item was added. Using array index as key breaks this optimization and can cause state bugs.
  • [MUST KNOW] Render phase vs Commit phase: Render phase = React builds new virtual DOM tree (can be paused/restarted by Fiber scheduler — this is why render must be pure, no side effects). Commit phase = React applies changes to real DOM (synchronous, cannot be interrupted). useEffect runs after commit phase.
  • [SHOULD KNOW] React Fiber: The reconciler algorithm introduced in React 16. Makes rendering interruptible — React can pause rendering work to handle higher-priority updates (like user input) and resume later. Enables concurrent features (Suspense, transitions). Pre-Fiber (React stack reconciler): rendering was synchronous and non-interruptible.
  • [SHOULD KNOW] Batching in React 18: React 18 automatically batches state updates even in async callbacks (setTimeout, Promises, native event handlers). Pre-React 18: batching only happened inside React event handlers. This reduces unnecessary re-renders.
Q: Explain the Virtual DOM and why React uses it.
Answer: The Virtual DOM is an in-memory JavaScript representation of the real DOM. When component state changes, React creates a new virtual DOM tree and diffs it against the previous one using a O(n) algorithm (Fiber reconciler). Only the actual changes are flushed to the real DOM in a batched commit phase.
React uses this for two reasons: (1) Real DOM operations trigger browser reflows and repaints, which are expensive. Batching and minimizing DOM mutations improves performance. (2) The virtual DOM lets React maintain a declarative programming model — you describe what the UI should look like, not how to update it. React figures out the minimal set of DOM operations needed.
Important nuance: the Virtual DOM is not free — there's overhead in diffing. For simple static UIs, direct DOM manipulation can be faster. React's value is for complex, frequently-updating UIs where the diffing overhead is outweighed by the benefit of optimized updates and declarative code.

Topic 2: React Hooks Deep Dive

useState

  • [MUST KNOW] Stale closure problem: If a callback captures a state variable and doesn't update when state changes, it reads the old value. Classic bug with setInterval + state.
  • [MUST KNOW] Functional updates: setState(prev => prev + 1) — always gets latest state, safe for async updates. Prefer over setState(count + 1) in async contexts.
// Stale closure bug
function Counter() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1); // BUG: count is always 0 (stale closure)
    }, 1000);
    return () => clearInterval(id);
  }, []); // empty deps — never re-registers

  // FIX: functional update
  useEffect(() => {
    const id = setInterval(() => {
      setCount(prev => prev + 1); // always gets latest value
    }, 1000);
    return () => clearInterval(id);
  }, []);
}

useEffect

  • [MUST KNOW] When it runs: After every render by default. After renders where specified deps changed (with dep array). Once on mount (empty dep array). Cleanup runs before next effect and on unmount.
  • [MUST KNOW] Common bugs: Missing dependency (stale value). Infinite loop (dependency is an object/function created in render — new reference each render → effect fires → state change → re-render → new reference → loop). Objects in deps: use useMemo or move the object outside the component.
  • [MUST KNOW] Cleanup: Return a function to clean up subscriptions, timers, event listeners. Without cleanup: memory leaks if component unmounts before async operation completes.
// Proper useEffect with cleanup + abort controller (for async fetches)
function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  
  useEffect(() => {
    const controller = new AbortController();
    
    async function fetchUser() {
      try {
        const res = await fetch(`/api/users/${userId}`, { signal: controller.signal });
        const data = await res.json();
        setUser(data);
      } catch (err) {
        if (err.name !== 'AbortError') console.error(err);
      }
    }
    
    fetchUser();
    return () => controller.abort(); // cleanup: abort if userId changes or component unmounts
  }, [userId]); // re-fetch when userId changes
}

useMemo & useCallback

  • [MUST KNOW] useMemo: Memoizes a computed value. Only recomputes when deps change. Use when: expensive computation (sorting, filtering large arrays), or when you need referential equality for an object passed to a child (but prefer redesigning props first).
  • [MUST KNOW] useCallback: Memoizes a function reference. The function is recreated only when deps change. Useful when passing callbacks to memoized children (React.memo) — without useCallback, function reference changes on every render, defeating memo.
  • [SHOULD KNOW] When NOT to use them: They have overhead (comparison of deps + memoization). Don't add them everywhere "just in case" — profile first. useMemo is only useful if the computation is genuinely expensive OR if referential equality matters for a dependency.
// useMemo for expensive computation
const sortedItems = useMemo(
  () => items.slice().sort((a, b) => b.price - a.price),
  [items] // only re-sort when items array changes
);

// useCallback to stabilize callback for React.memo child
const handleDelete = useCallback((id) => {
  setItems(prev => prev.filter(item => item.id !== id));
}, []); // no deps: setItems is stable

// React.memo to skip re-render if props unchanged
const ItemList = React.memo(function ItemList({ items, onDelete }) {
  // only re-renders if items or onDelete reference changes
  return items.map(item => );
});

useRef

  • [MUST KNOW] Two use cases: (1) DOM access — ref.current is the actual DOM node. Used for focus management, measuring elements, triggering animations. (2) Mutable value that persists across renders without triggering re-render — unlike state. Use for tracking previous values, storing timers, tracking if component is mounted.

Custom Hooks

  • [MUST KNOW] What they are: Functions starting with use that use other hooks internally. Extract reusable stateful logic from components. The same as extracting logic into a utility function, but for stateful logic.
// Custom hook: useDebounce
function useDebounce(value, delay) {
  const [debouncedValue, setDebouncedValue] = useState(value);
  useEffect(() => {
    const timer = setTimeout(() => setDebouncedValue(value), delay);
    return () => clearTimeout(timer);
  }, [value, delay]);
  return debouncedValue;
}

// Custom hook: useFetch
function useFetch(url) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);
  
  useEffect(() => {
    const controller = new AbortController();
    setLoading(true);
    fetch(url, { signal: controller.signal })
      .then(r => r.json())
      .then(setData)
      .catch(e => { if (e.name !== 'AbortError') setError(e); })
      .finally(() => setLoading(false));
    return () => controller.abort();
  }, [url]);
  
  return { data, loading, error };
}
Q: Explain useCallback. When does it actually help and when is it useless?
Answer: useCallback memoizes a function reference so the same function instance is returned across renders if dependencies haven't changed. It's useful when: (1) Passing a callback to a React.memo-wrapped child component — without useCallback, every render creates a new function reference, which React.memo sees as a prop change and re-renders the child unnecessarily. (2) Using a function as a useEffect dependency — stable reference prevents the effect from re-running on every render.
It's useless when: (1) The child is not wrapped in React.memo — it re-renders anyway regardless. (2) The component re-renders only occasionally — the memoization overhead isn't worth it. (3) You're optimizing prematurely without profiling first.
The pattern: useCallback only makes sense when paired with React.memo on the child, or as a useEffect dependency. Without either of those, you're paying the memoization cost for no benefit.

Topic 3: State Management

When to Escalate State

  • [MUST KNOW] Local state first (useState): Component-specific UI state — modal open/closed, form input values, loading flags. Don't reach for global state by default.
  • [MUST KNOW] Context API: Good for: theme, locale, auth user, anything that changes infrequently. Bad for: frequently changing data (every Context update re-renders all consumers — use separate contexts or split contexts by update frequency). Not a performance solution for high-update-rate state.
  • [MUST KNOW] Redux Toolkit: For complex shared state with many interactions. Slice pattern: each feature gets a slice with state, reducers, actions. createAsyncThunk for async actions. RTK Query for server state + caching (replaces custom fetch logic). Don't use Redux for UI state or server cache — that's overengineering.
  • [SHOULD KNOW] React Query / TanStack Query: Server state management — fetching, caching, synchronizing, background updates. The stale-while-revalidate pattern: serve stale data immediately while refetching in background. Eliminates most of what people use Redux for (server data in Redux). Use React Query for API data, keep Redux (or Zustand) only for client-side app state.
  • [SHOULD KNOW] Zustand: Minimal global store without Redux boilerplate. Simple API — just a function. No providers needed. Good for medium complexity apps where Redux is overkill.
Q: When would you use Redux Toolkit vs React Query vs Context API?
Answer: These solve different problems and ideally are used together:
React Query: Server state — data that lives on the server and needs to be fetched, cached, synchronized, and invalidated. User lists, posts, product catalog. It handles loading/error states, background refetching, cache invalidation, optimistic updates. This is where most "Redux for API data" anti-patterns come from — React Query does it better.
Redux Toolkit: Complex client-side app state — shopping cart, multi-step form wizard, undo/redo history, anything that multiple unrelated components need to read/write with complex logic. Use when state transitions are complex enough to benefit from Redux DevTools and the predictable state container model.
Context API: Low-frequency global values — current user/auth, theme, locale. Avoid for high-frequency updates.
useState/useReducer: Component-local state first. Always start here.
In a real app: React Query for all server data, Zustand or Redux Toolkit for complex client state, Context for auth/theme.

Topic 4: Performance Optimization

Component-Level Optimization

  • [MUST KNOW] React.memo: HOC that skips re-render if props are shallowly equal. Use for pure components that re-render too often with same props. Must be combined with stable callback references (useCallback) to be effective.
  • [MUST KNOW] Code Splitting: React.lazy() + Suspense for lazy-loading components. Split by route (each route is a separate chunk) — most impactful. Split by feature (heavy modals, charts). Reduces initial bundle size and time-to-interactive.
  • [SHOULD KNOW] List Virtualization: For long lists (100+ items), only render visible items. Libraries: react-window (lightweight), react-virtualized. Critical for tables, infinite scroll feeds, large option lists.
  • [SHOULD KNOW] Avoiding unnecessary re-renders: (1) Move state down — if state only affects a subtree, keep it in that subtree's root. (2) State colocation — don't lift state higher than necessary. (3) Split contexts — separate Context for frequently-changing vs static values. (4) Profile first using React DevTools Profiler.

Topic 6: JavaScript Fundamentals (Still Asked at 4–5 YOE)

Closures

// Closure: function retains access to its lexical scope even when executed outside it
function makeCounter() {
  let count = 0; // in closure scope
  return {
    increment: () => ++count,
    decrement: () => --count,
    value: () => count
  };
}
const counter = makeCounter();
counter.increment(); // 1
counter.increment(); // 2
counter.value(); // 2
// count is private — only accessible through the returned functions

  • [MUST KNOW] Every JavaScript object has a hidden [[Prototype]] property pointing to another object (or null). Property lookup walks up the prototype chain. Object.create(proto) creates an object with proto as its prototype. ES6 class syntax is syntactic sugar over prototype chains.

Q: What is a closure and give a practical use case in a React app?
Answer: A closure is when an inner function retains access to variables in its outer function's scope even after the outer function has returned. The function "closes over" those variables.
In React, closures are everywhere. The most practical example: event handler callbacks. When you write onClick={() => handleDelete(item.id)}, the arrow function closes over item.id from the render scope. Each item in the list has its own closure capturing its specific ID.
The stale closure bug is the most important React closure pitfall: if you capture state in a closure (e.g., inside setInterval) without listing it as a dependency, you get the state value from when the closure was created, not the current value. Fix: either add to dependency array (recreates the closure when state changes) or use the functional update form (setState(prev => ...)) which doesn't need the current state value from closure.
