Topic 1: SQL vs NoSQL — The Decision Framework

This is always asked. Don't say "it depends" without explaining exactly what it depends on.

FactorChoose SQL (PostgreSQL/MySQL)Choose NoSQL (MongoDB/DynamoDB)
Data structureStructured, consistent schema, clear relationshipsVariable schema, nested/hierarchical data, frequent schema changes
Query patternsComplex queries, JOINs, aggregations, ad-hoc queriesKnown access patterns, key-value lookups, document-centric reads
ConsistencyStrong consistency required (financial, medical)Eventual consistency acceptable (social, analytics)
ScaleVertical + read replicas handles most use casesBuilt for horizontal write scaling out of the box
TransactionsACID transactions across multiple records/tablesMongoDB supports transactions but performance cost is high
Team expertiseTeam knows SQL well (almost always)Specific use case that SQL handles poorly
Common Wrong Answers: "NoSQL is faster than SQL" — false. A properly indexed PostgreSQL query is faster than a MongoDB query in most cases. "NoSQL scales, SQL doesn't" — PostgreSQL with read replicas scales to millions of requests/day for most applications. Don't jump to NoSQL without a concrete reason.
Q: When would you choose MongoDB over PostgreSQL for a new project?
Answer: I'd choose MongoDB when: (1) The data is genuinely document-shaped — e.g., e-commerce product catalog where each product category has wildly different attributes. Forcing this into relational tables requires many nullable columns or a EAV pattern, both painful. (2) Schema evolves rapidly in early startup phases — MongoDB's flexible schema lets you iterate fast before the data model stabilizes. (3) The access patterns are always "load this user's entire profile" — document model means you get the whole document in one read without JOINs.
I'd stay with PostgreSQL for: anything with complex relational queries, reporting/analytics (SQL is far more expressive), anything requiring strong ACID transactions, and anywhere the team knows SQL well. PostgreSQL with JSONB can also handle semi-structured data, giving you the flexibility of document storage with relational SQL power.

Topic 2: Indexing — The Most Asked DB Topic

B-Tree Index Internals (Know the Concept, Not the Code)

  • [MUST KNOW] What a B-Tree index is: A self-balancing tree data structure. Leaf nodes contain the indexed column values pointing to the actual table rows (heap tuples). Tree is kept balanced so any lookup is O(log N) instead of O(N) full table scan. An index on a 10M row table has ~log_100(10M) ≈ 3–4 node reads to find a value — extremely fast.
  • [MUST KNOW] When indexes help: Equality lookups (WHERE id = 5), range queries (WHERE created_at > '2024-01-01'), ORDER BY (if index matches sort direction), JOIN columns, WHERE clause columns with high cardinality (many distinct values).
  • [MUST KNOW] When indexes do NOT help (or hurt): Low cardinality columns (boolean, status with 3 values — full table scan faster). Very small tables (<1000 rows). Write-heavy tables (index must be maintained on every INSERT/UPDATE/DELETE — overhead). Wildcard leading search (LIKE '%john' — can't use index). Functions on indexed column (WHERE LOWER(email) = 'x' — create a functional index instead).
  • [MUST KNOW] Composite Index Column Order: Rule: most selective column first. Or: match your most common query's WHERE clause order. Index on (a, b, c) can be used for queries on (a), (a, b), or (a, b, c) — but NOT (b) alone or (b, c) alone (leftmost prefix rule).
  • [SHOULD KNOW] Covering Index: Index that contains all columns needed for a query — no need to read the actual table rows (heap). Example: query SELECT email FROM users WHERE status = 'active' — an index on (status, email) is a covering index. Eliminates random I/O to table. Significant performance boost for read-heavy queries.
  • [SHOULD KNOW] Index Selectivity: High selectivity = few rows match = index very useful. Low selectivity = many rows match = index less useful (reading many pages, might as well scan). Rule of thumb: if a query returns >10–15% of rows, DB may choose a full table scan over the index.
-- How to read EXPLAIN output (PostgreSQL)
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 123 AND status = 'pending';

-- Good output (using index):
Index Scan using idx_orders_user_status on orders
  Index Cond: ((user_id = 123) AND (status = 'pending'))
  Actual rows: 15  Actual time: 0.05ms

-- Bad output (not using index):
Seq Scan on orders  -- sequential scan = full table
  Filter: ((user_id = 123) AND (status = 'pending'))
  Rows Removed by Filter: 995000
  Actual rows: 15  Actual time: 312ms  -- 6000x slower

-- Fix: create composite index
CREATE INDEX idx_orders_user_status ON orders (user_id, status);
-- user_id first (higher cardinality), status second (low cardinality but used in query)
Q: You have a query: SELECT * FROM orders WHERE user_id = 123 AND status = 'pending' ORDER BY created_at DESC. Design the optimal index.
Answer: The optimal index is CREATE INDEX ON orders (user_id, status, created_at DESC);
Reasoning: user_id goes first — highest cardinality, most selective, will filter to just this user's orders. status goes second — low cardinality alone but here it further filters. created_at DESC goes last — allows sorting without a separate sort operation. The index serves the full query: equality on user_id, equality on status, ordered scan on created_at. This is also nearly a covering index (missing only the columns in SELECT *; if we only needed specific columns, we'd add them to make it covering). If the query uses a LIMIT clause, the DB can stop scanning after N rows instead of sorting everything.

Topic 3: ACID Properties & Transactions

ACID — Examples Are Essential

  • [MUST KNOW] Atomicity: All operations in a transaction succeed, or all are rolled back. Example: transferring $100 — debit account A AND credit account B must both succeed, or neither happens. Implemented via undo logs.
  • [MUST KNOW] Consistency: Transaction brings DB from one valid state to another. All constraints (foreign keys, unique, NOT NULL, check constraints) must hold before and after. Example: you can't transfer $100 if account A has $50 — the constraint (balance >= 0) would be violated.
  • [MUST KNOW] Isolation: Concurrent transactions don't see each other's intermediate state. The tricky one — isolation level determines exactly how much isolation you get. See below.
  • [MUST KNOW] Durability: Committed transactions survive crashes. Implemented via Write-Ahead Log (WAL) — changes written to log before being applied to data files. On crash recovery, replay the log.

Isolation Levels

  • [MUST KNOW] Dirty Read: Reading uncommitted data from another transaction. T1 writes X=10 (not committed), T2 reads X=10, T1 rolls back — T2 used incorrect data.
  • [MUST KNOW] Non-Repeatable Read: Same row read twice in one transaction gives different results because another transaction committed an update in between.
  • [MUST KNOW] Phantom Read: Range query returns different rows on second read because another transaction inserted/deleted rows matching the range.

Deadlocks

  • [MUST KNOW] How deadlocks occur: T1 locks row A then tries to lock row B. T2 has row B locked and tries to lock row A. Circular wait — neither can proceed. DB detects and kills one transaction (rolls it back), returning an error.
  • [MUST KNOW] Prevention: Always acquire locks in the same consistent order across all transactions. Use shorter transactions (hold locks for less time). Use SELECT FOR UPDATE SKIP LOCKED for queue-like patterns.
  • [SHOULD KNOW] Optimistic vs Pessimistic Locking: Pessimistic = lock rows before reading/updating (SELECT ... FOR UPDATE). Good when conflicts are frequent. Optimistic = no locks; at commit time, check if data changed since read (version column or timestamp). Good when conflicts are rare — avoids lock overhead. Use a version column: UPDATE items SET qty = qty-1, version = version+1 WHERE id = 5 AND version = 3 — if 0 rows affected, conflict occurred.
Q: Explain ACID with a bank transfer example. What isolation level would you use?
Answer: Transfer $100 from account A to account B:
Atomicity: Both the debit (A -= 100) and credit (B += 100) are in one transaction. If the credit fails, the debit is rolled back — you don't lose money.
Consistency: Business rule: balance cannot go below 0. The transaction enforces this — if A has $50, it's rejected before any changes happen.
Isolation: If two transfers happen simultaneously, isolation prevents them from reading each other's partial state. Without isolation, two concurrent transfers of $100 from the same $150 account could both think there's enough balance — both succeed — but total is $250 withdrawn from $150 (race condition).
Durability: Once you get "transfer confirmed," the data is written to disk via WAL. A server crash right after doesn't lose the transfer.
Isolation Level: SERIALIZABLE for financial transactions — complete isolation prevents any concurrent anomalies. The performance cost is acceptable because money correctness is non-negotiable.

Topic 4: Advanced SQL

N+1 Problem

  • [MUST KNOW] What it is: Fetching a list of N records, then making N additional queries to fetch related data — total: N+1 queries. Example: fetch 100 posts (1 query), then for each post fetch the author (100 queries) = 101 queries. Destroys performance at scale.
  • [MUST KNOW] Solutions: (1) Eager loading with JOIN — fetch posts and authors in one query. (2) DataLoader (Node.js) — batch and deduplicate queries within a single request cycle (essential for GraphQL). (3) SQL IN clause — fetch all 100 author IDs in one query: WHERE id IN (1, 2, ...100). (4) ORM includes: Mongoose .populate(), Sequelize include:.

CTEs and Window Functions

-- CTE (Common Table Expression) — WITH clause
-- Use for: breaking complex queries into readable steps, recursive queries
WITH monthly_revenue AS (
  SELECT 
    DATE_TRUNC('month', created_at) AS month,
    SUM(amount) AS revenue
  FROM orders
  WHERE status = 'completed'
  GROUP BY 1
),
ranked AS (
  SELECT 
    month, revenue,
    LAG(revenue) OVER (ORDER BY month) AS prev_month_revenue
  FROM monthly_revenue
)
SELECT 
  month,
  revenue,
  prev_month_revenue,
  ROUND((revenue - prev_month_revenue) / prev_month_revenue * 100, 2) AS growth_pct
FROM ranked
ORDER BY month;

-- Window Functions — calculations across rows related to current row
-- ROW_NUMBER: unique sequential row number
SELECT 
  id, user_id, amount,
  ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
FROM orders;
-- Use this to get "latest order per user" by filtering WHERE rn = 1

-- RANK vs DENSE_RANK: RANK leaves gaps (1,2,2,4). DENSE_RANK doesn't (1,2,2,3)
-- LAG/LEAD: access previous/next row value
-- SUM/AVG OVER: running totals, moving averages
Q: Write a query to find the top 3 customers by total spend per country.
WITH customer_spend AS (
  SELECT 
    c.id AS customer_id,
    c.name,
    c.country,
    SUM(o.amount) AS total_spend
  FROM customers c
  JOIN orders o ON o.customer_id = c.id
  WHERE o.status = 'completed'
  GROUP BY c.id, c.name, c.country
),
ranked AS (
  SELECT *,
    DENSE_RANK() OVER (PARTITION BY country ORDER BY total_spend DESC) AS rank
  FROM customer_spend
)
SELECT customer_id, name, country, total_spend, rank
FROM ranked
WHERE rank <= 3
ORDER BY country, rank;
Key points to explain: Using DENSE_RANK so ties don't cause fewer than 3 results per country. CTE for readability and reuse. PARTITION BY country to reset ranking per country. Filtering on PARTITION+RANK is the classic pattern for "top N per group" — interviewers love this.

Topic 5: MongoDB Deep Dive

Aggregation Pipeline

  • [MUST KNOW] Core pipeline stages: $match (filter — put early to reduce documents), $group (aggregate — like SQL GROUP BY), $project (shape output — include/exclude/compute fields), $sort, $limit, $skip (pagination), $lookup (JOIN — performance-sensitive, use sparingly), $unwind (flatten arrays)
// Find top 5 categories by total revenue, last 30 days
db.orders.aggregate([
  // Stage 1: filter recent orders
  { $match: { 
    status: 'completed',
    createdAt: { $gte: new Date(Date.now() - 30*24*60*60*1000) }
  }},
  // Stage 2: unwind items array (one doc per item)
  { $unwind: '$items' },
  // Stage 3: group by category
  { $group: {
    _id: '$items.category',
    totalRevenue: { $sum: { $multiply: ['$items.price', '$items.quantity'] } },
    orderCount: { $sum: 1 }
  }},
  // Stage 4: sort by revenue desc
  { $sort: { totalRevenue: -1 } },
  // Stage 5: top 5 only
  { $limit: 5 },
  // Stage 6: reshape output
  { $project: {
    category: '$_id',
    totalRevenue: { $round: ['$totalRevenue', 2] },
    orderCount: 1,
    _id: 0
  }}
]);

MongoDB Indexes

  • [MUST KNOW] Single field index, compound index (same leftmost prefix rule as SQL), text index (full-text search), 2dsphere (geospatial). db.collection.createIndex({field: 1}) (1 = ascending, -1 = descending).
  • [SHOULD KNOW] Index strategies for MongoDB: explain("executionStats") to check if index is used. COLLSCAN (collection scan) = no index used = slow. IXSCAN = index used = fast. Sparse indexes (only index documents that have the field). Partial indexes (index only documents matching a filter).
  • [SHOULD KNOW] Replica Sets: Primary handles writes. Secondaries replicate asynchronously. If primary fails, secondaries elect a new primary (Raft-like election). Read preference: primary (default, consistent), secondaryPreferred (better read performance, slight staleness).
Q: When would you use $lookup vs embedding in MongoDB?
Answer: This is a schema design decision. Embed when: the subdocument is always accessed with its parent (user profile → user address), the subdocument doesn't grow unboundedly, you don't need to query the subdocument independently. Use references + $lookup when: the referenced entity is shared across multiple documents (orders → products — one product referenced by many orders), the referenced document changes frequently (embed would require updating many documents), the subdocument could grow unboundedly (user → posts — don't embed all posts in the user document).
Practical rule: embed for "is a part of" relationships. Reference for "is related to" relationships. And be aware that $lookup is a cross-collection join in MongoDB — it's less efficient than embedding and can be a performance bottleneck at high volume. Design your schema around your primary access patterns.

Data Structures and When to Use Them

Common Redis Patterns

  • [MUST KNOW] Distributed Lock: SET lock:resource uniqueId NX EX 30 — NX = only set if not exists, EX 30 = expire in 30 seconds. Release: only release if value matches uniqueId (Lua script for atomicity). Prevents race conditions across distributed services. Note: single Redis instance lock is not truly safe under partitions (use Redlock algorithm for multi-node).
  • [MUST KNOW] Rate Limiting: INCR + EXPIRE pattern: INCR rate:userId:minute → if == 1: EXPIRE rate:userId:minute 60 → if result > limit: reject. Or sorted set sliding window (see System Design doc).
  • [MUST KNOW] Session Storage: SET session:sessionId {userId, roles, ...} EX 3600. On request: GET session:sessionId. On logout: DEL session:sessionId. Instant revocation — unlike JWTs.
  • [SHOULD KNOW] Pub/Sub: Publisher: PUBLISH channel message. Subscriber: SUBSCRIBE channel. Fire-and-forget — no message persistence. Messages lost if subscriber is offline. Use for real-time events between services when message loss is acceptable. Use Redis Streams for durability.
  • [SHOULD KNOW] Persistence: RDB (snapshot) — periodic point-in-time snapshots to disk. Fast restart, but data loss between snapshots. AOF (Append-Only File) — log every write operation. Slower restart, less data loss. Most production setups: AOF with RDB as backup. appendfsync everysec — sync to disk every second (max 1 second data loss).
Q: How would you implement a leaderboard for a gaming app using Redis?
Answer: Perfect use case for Sorted Sets. Score = player's points, member = playerId. 
// Add/update player score
await redis.zadd('leaderboard:global', score, userId);

// Get top 10 players with scores (descending)
const top10 = await redis.zrevrange('leaderboard:global', 0, 9, 'WITHSCORES');

// Get a player's rank (0-indexed, so +1)
const rank = await redis.zrevrank('leaderboard:global', userId);

// Get players around a specific player (neighborhood rank)
const myRank = await redis.zrevrank('leaderboard:global', userId);
const neighborhood = await redis.zrevrange('leaderboard:global', 
  Math.max(0, myRank - 5), myRank + 5, 'WITHSCORES');
Sorted Sets give O(log N) insert/update and O(log N + K) range query where K is result size. For a 10M player leaderboard, this is still extremely fast. For multiple leaderboards (daily/weekly/global): separate keys with TTL on time-based ones. For regional leaderboards: key per region.

Topic 7: Database Schema Design

Normalization (Know the Concepts)

  • [MUST KNOW] 1NF: Atomic values — no repeating groups, no arrays in a column. Each row uniquely identified.
  • [MUST KNOW] 2NF: 1NF + no partial dependencies. Every non-key column depends on the entire primary key (relevant for composite keys).
  • [MUST KNOW] 3NF: 2NF + no transitive dependencies. Non-key columns depend only on the primary key, not on other non-key columns. Example: if Employee table has DeptName and DeptLocation — DeptLocation depends on DeptName, not directly on EmployeeId. Fix: separate Department table.
  • [SHOULD KNOW] Denormalization: Intentionally violate normalization for read performance. Store derived/aggregated data to avoid expensive JOINs. Trade-off: write complexity (maintain denormalized copies) vs read speed. Common in reporting, analytics, high-read systems.

Schema Design Exercise

Q: Design the database schema for an e-commerce order system (PostgreSQL).
-- Users
CREATE TABLE users (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email       VARCHAR(255) UNIQUE NOT NULL,
  name        VARCHAR(255) NOT NULL,
  created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- Products
CREATE TABLE products (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name        VARCHAR(255) NOT NULL,
  price       DECIMAL(10,2) NOT NULL CHECK (price >= 0),
  stock_qty   INTEGER NOT NULL DEFAULT 0 CHECK (stock_qty >= 0),
  category_id UUID REFERENCES categories(id),
  created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- Orders
CREATE TABLE orders (
  id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id        UUID NOT NULL REFERENCES users(id),
  status         VARCHAR(50) NOT NULL DEFAULT 'pending' 
                   CHECK (status IN ('pending','paid','shipped','delivered','cancelled')),
  total_amount   DECIMAL(10,2) NOT NULL,
  idempotency_key VARCHAR(255) UNIQUE, -- prevents duplicate orders
  created_at     TIMESTAMPTZ DEFAULT NOW()
);

-- Order items (many-to-many: orders ↔ products)
CREATE TABLE order_items (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id    UUID NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  product_id  UUID NOT NULL REFERENCES products(id),
  quantity    INTEGER NOT NULL CHECK (quantity > 0),
  unit_price  DECIMAL(10,2) NOT NULL, -- snapshot price at time of order
  UNIQUE(order_id, product_id)
);

-- Key indexes
CREATE INDEX idx_orders_user_id ON orders (user_id);
CREATE INDEX idx_orders_status_created ON orders (status, created_at DESC);
CREATE INDEX idx_order_items_order ON order_items (order_id);
Key design decisions to explain: UUID primary keys (vs serial integers) — portable, no centralized counter needed. unit_price in order_items — snapshot the price at order time, not a FK to current price (prices change). idempotency_key on orders — prevents duplicate orders from network retries. ON DELETE CASCADE on order_items — deleting an order deletes its items. CHECK constraints enforce business rules at DB level.
